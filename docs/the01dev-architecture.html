How the platform is built and how a request moves through it

A personalised learning platform: students buy courses, ask a tutor grounded in lecture transcripts, take adaptive quizzes, and turn their own notes into study material. This describes the system as it stands — read each diagram first and use the text to recover the decision or boundary behind it. Every claim was read from the code.

Chapter 2 — How a question is answered

Recall structure: GATE → CLASSIFY → SHORT-CIRCUIT → STREAM → RECONCILE. Every component in the tutor path belongs to one of these five responsibilities.

A student asks “What are cgroups and namespaces in Linux?” — a topic no course covers. The system answers it, cites nothing it cannot ground, and claims no enrolment that does not exist.

One question: what changes at every boundary
1Browser — the untrusted request POST /api/hermes/chat carries the question, the course slug and student_id (the Firebase UID from the signed-in session).
Client suppliesquestion · course_slug · student_id
Client never suppliesentitlement · mastery · citations · billing
2Access gate, then one PII choke point Entitlement is checked server-side, then pii.scrub() runs — deliberately a single choke point rather than scattered redaction, so there is one place to audit before anything leaves.
3Deterministic intent classification classify() is regex, not a model: COURSE_QUESTION · QUIZ_GENERATE · OUT_OF_SCOPE. A second embedding check catches smalltalk by cosine similarity and runs observe-only — it logs what it would have blocked without acting.
4Short-circuit before spending a model call Only QUIZ_GENERATE and OUT_OF_SCOPE short-circuit, fake-streaming a hand-off in the same SSE shape the client already parses, so the UI needs no special case. Everything else — including the Linux question — goes to the agent.
5Stream through the agent runtime hermes_client.stream_chat() posts to Hermes's /v1/chat/completions and relays SSE tokens to the browser. Hermes resolves every tool call internally; the backend sees tokens and side-effects, never tool traffic.
6Reconcile citations out of band Since the backend cannot observe search_course_content, the MCP tool writes its source cards to chat_citations/{student_id}. The route clears that key before the turn, reads it back after the stream, and emits a second sources event.
Clear-before, read-after. Clickable citations look like a frontend feature. They are not: the agent resolves tools in its own process, so the backend has no hook on retrieval. The side channel is keyed by student and cleared at the start of each turn, so one answer's sources can never leak into the next.

The agent boundary

The main architectural fact of this system
Backend — FastAPI, single worker Owns entitlement, PII scrub, intent routing, the SSE relay, the database
Hermes agent runtime — separate service, port 8642 Owns the reasoning loop, tool selection and execution. Auth: bearer HERMES_API_KEY
MCP subprocess — the01dev_tools.py over stdio Ten tools with real database reach. Writes side-effects the backend reads afterwards.
The backend cannot observe the middle layer's decisions. Anything it must know has to be written somewhere it can read — which is why citations use a store key rather than a return value.

The corpus is loaded from a static seed file of lecture transcripts. There is no ingestion endpoint — adding a course means shipping data, not calling an API.

The rule that makes the tutor useful

Answer everything, cite only what you can ground. The course is an enrichment, never a gate. The agent searches course content first; when it finds something it grounds the answer and cites the lecture, and when it does not it answers from general knowledge while being clear the answer is not course-cited. A student learning React still hits a Linux question at 1am, and refusing it is the wrong product.

The one thing it must refuse. Not topics — facts it cannot know. Payment and billing state have no tool behind them, so the agent hands off rather than guesses. The distinction is “unknowable”, not “off-syllabus”.

Least privilege, and what it bought. The Hermes profile pins platform_toolsets.api_server: [memory]. Without that entry the OpenAI-compatible endpoint falls back to the runtime's default toolset, which grants terminal execution, arbitrary file read/write and browser automation over plain HTTP behind one shared key. Restricting it also cut prompt tokens from roughly 30k to 8k per request, because far fewer tool schemas ship with every call — the safety fix paid for itself in cost and latency.

Chapter 4 — Lab: the content pipeline

Recall structure: INGEST → SELECT → FAN OUT → PERSIST → QUIZ. One LangGraph run; artifacts finish before the long-lived interactive part begins.

The governing product principle: students should not have to adapt to a hard-coded concept schema — they learn what they want, and it is the platform's job to keep track of it.

Why artifacts are sequenced, not a sibling branch. If the quiz branch interrupts in the same superstep as the generators, whether finished artifacts are durable at suspend time depends on the framework's pending-write semantics. Sequencing removes the question: work the student already earned is saved before anything long-lived starts.
No approval gate on artifacts, by design. The student already ticked the boxes. Human-in-the-loop earns its place on the quiz's objectives plan — reviewing what you will be tested on is real value — not on confirming what you just asked for.

Chapter 5 — The learner model

Recall structure: OBSERVE → SCORE → READ BACK. Quizzes and chat observations write mastery; agent tools read it back so the tutor can speak to it.
Two quiz systems, deliberately separate
Course quiz — adaptivePre-authored bank scoped to a purchased course. Selects by accuracy band, resurfaces on a 3-day spaced interval, writes concept_performance keyed user__concept and a per-answer quiz_sessions row.
Lab quiz — ad hocGenerated from whatever the student brought, with hints and a Socratic tutor. Interactive, but does not write mastery.
They are different products: one measures progress against a syllabus, the other helps a student study anything. Keeping the write path separate is what stops ad-hoc concept names fragmenting the graph.

The open concept space next

Self-study does not yet count toward mastery. The design that closes it is a single resolver every concept write passes through, so a student's own material lands in the same graph as course material:

1 · slugify“React.memo” → react-memo
→
2 · exact slugfree — no model call
→
3 · embeddingcosine ≥ 0.64 → merge
→
4 · createno match → new concept node
Notes on closures merge onto the existing course concept and move real course mastery. Notes on Kubernetes, which no course covers, create a node. The graph grows to fit the student.
Where 0.64 comes from. Measured across 31 pairs: true matches cluster at 0.709–0.755, false matches cap at 0.578. The band between is empty and 0.13 wide; 0.64 is its midpoint. Short concept names do not score like sentences — even React.memo against react-memo only reaches 0.755, so a high threshold merges nothing. Expect it to rise as the pool grows: with 9 concepts there are 9 chances to draw a spurious high score, with 500 there are 500. It is a starting point with a monitoring plan, not a constant.

Chapter 6 — Data and storage

Recall structure: ONE TABLE → MANY COLLECTIONS → UPSERT SEMANTICS. A document store built on Postgres, plus one real vector table.

→

First match wins. The in-memory fallback is the reason a test suite can be entirely green while a database-specific bug sits in the code — see chapter 7.

Every collection lives in one table: docs(collection, doc_id, data jsonb) with a composite primary key on (collection, doc_id). Every write is therefore an upsert — a doc id that is not unique silently overwrites. Embeddings live separately in rag_chunks with pgvector.

audit_logPer-turn records for reconstructing a past answer
recommendations · study_guidesDerived guidance surfaces
rag_chunksTranscript chunks + embeddings (its own pgvector table, not in docs)
Doc ids are the integrity mechanism. Because every write upserts, an id that is not scoped to the student overwrites another student's row with no error. Mastery is keyed user__concept for exactly this reason — and changing how a concept is spelled changes its id, which is why concept names are normalised on the write path and existing rows are never rewritten.

Chapter 7 — Operating it

Recall structure: ONE WORKER → BLOCKING IS THE RISK → VERIFY WHAT SHIPPED. The constraints that hold in this system, and the two rules that keep it up.
Everything below shares one uvicorn worker
SSE chat streamslong-lived, one per active student
RAG searchembed + pgvector query
Lab generationseveral model calls per run
PDF parsingCPU-bound — routed off the loop
PaymentsRazorpay callbacks
Health checksRailway polls these
This is why blocking work is the first-order risk: a synchronous PDF parse would stall the health check and every open chat stream at once. It runs in a threadpool for exactly that reason.
Rule 1 — never bridge async work with asyncio.run(). The asyncpg pool is created once per process and is bound to the event loop that created it. asyncio.run() makes a new loop, so the cached pool is then used from a foreign one and fails with InterfaceError: cannot perform operation: another operation is in progress. Tests cannot see this: without DATABASE_URL they use the in-memory store, where the same write is a dict assignment. Do the I/O in the async route, or hand it to a threadpool — never spin a second loop.
Rule 2 — a local frontend build cannot see Netlify's env vars. .env.local is gitignored and site-level variables only apply to builds Netlify runs itself, so a local npm run build falls through to the in-code default and bakes http://localhost:8080 into the bundle — for the API, Lab and payments. It typechecks, builds and loads; every server call then fails in the visitor's browser. Pass the variables on the build command, and afterwards grep the built bundle for its API base. Checking that a bundle lacks some old string proves nothing about what it points at.
Known limitState and reasoning
In-memory graph checkpointsA redeploy loses in-flight Lab sessions — an upload and an unapproved plan. Never past work: artifacts persist as the run joins. A Postgres checkpointer is a drop-in upgrade when this hurts.
No eviction on the doc cacheUploaded text is held for the process lifetime, bounded by the 200k-char and 10 MB caps rather than a TTL.
Chunked uploads bypass the size checkThe pre-read rejection reads Content-Length; a chunked body with no such header still materialises before the post-read check. A fast path for honest clients, not a bound.
Library reads trust a client-supplied idAn unauthenticated read of another student's generated material. Consistent with the app's existing pattern; wants a product decision about auth across all these routes.
Admin gate is open when unsetrequire_admin_key allows the request if the env var is missing, so the key must actually be set in the environment.
SOUL hash reads a stale pathaudit_service.py:17 resolves the prompt file through an old home-relative path, so its integrity hash returns "unknown". The audit trail records the turn correctly but cannot prove which prompt version produced it.

Why this stack

QuestionAnswer
Why an agent runtime, not a plain model loop?Tool-calling, memory and the reasoning loop come built. The cost is that tool execution happens where the backend cannot see it, which is what forced the citation side channel
Why regex intent routing, not an LLM router?Three outcomes, zero latency, fully inspectable — and it only isolates the two cases that must not reach the model
Why one jsonb table, not a schema?The domain is still moving; a composite primary key gives upsert semantics for free. A deliberate trade against query power
Why Postgres for entitlement when Firebase is there?Entitlement joins against progress and the learner model. Firebase keeps what it is good at — auth and file storage
Why LangGraph for Lab?The quiz needs human-in-the-loop interrupts and resumable state. That is the framework's job; the fan-out is incidental
Why sequence artifacts before the quiz?Durability at suspend time stops being a question, and finished work is never held hostage by a long-lived tail

If something breaks

  1. Bound the impact. Who is affected, and is a rollback faster than a fix?
  2. Trace one request. Browser → route → intent → agent → tool → store → response.
  3. Find the first abnormal boundary. Do not guess from the symptom the UI shows.
  4. Reproduce against the real dependency. A green suite proves nothing about the database when tests swap it for a dict.
  5. Add a guard you watched fail. Break the code, see the test fail, revert. Only then does it count.

Spoken summary

  • the01.dev is a personalised learning platform: paid courses, a tutor grounded in lecture transcripts, adaptive quizzing, and a pipeline that turns a student's own notes into study material.
  • A question is gated for entitlement, scrubbed once, routed by deterministic regex, and streamed through an agent runtime resolving a deliberately restricted toolset.
  • Citations return through a side channel, because the agent resolves tools where the backend cannot observe them — cleared before each turn so one answer's sources never leak into the next.
  • The course is an enrichment, not a gate: answer everything, cite only what retrieval grounds, refuse only what the system genuinely cannot know.
  • Lab is one LangGraph run whose artifacts are sequenced ahead of the interactive quiz tail, so finished work survives a suspend.
  • Everything persists to one jsonb table where every write is an upsert, which makes doc-id scoping the integrity mechanism.
